# VratiMe contact email worker

`vratime-contact-mailer.py` sends only queued contact-exchange emails, using the existing VratiMe Gmail SMTP sender. Each initial exchange transaction inserts one private job per participant and one inbox item per participant. Historical exchanges are not backfilled with email jobs. The UI never claims email delivery based on queue creation.

Configuration is `/etc/vratime-mailer/config.json`, owned by root, mode 0600, never committed. Required keys: `supabase_url`, `supabase_service_key`, `smtp_host`, `smtp_port`, `smtp_user`, `smtp_password`, `from_email`, `from_name`. The worker restricts destinations for credentials to the specific VratiMe Supabase project and `smtp.gmail.com:587`; it uses verified STARTTLS. Existing configuration must be backed up privately before replacement. Provisioning existing secrets to a new host needs explicit owner authorization. Do not print secrets or put them in shell arguments.

Install the reviewed script as `/opt/vratime-mailer/vratime-contact-mailer.py`, install its supplied systemd service/timer, and first run `python3 /opt/vratime-mailer/vratime-contact-mailer.py --check`. That check authenticates SMTP without sending a message. Only then enable the timer. A missing config prevents service execution and does not consume job attempts. The timer runs once per minute, maximum five emails per execution. It is independent of the Telegram/support/media services.

The database grants claim/finish RPC access to service_role only. Claim leases a job for five minutes, resolves the recipient's verified Auth email, and suppresses jobs with no verified email. Participants cannot inspect the mail queue or supply a destination address. The message includes only their counterpart's shared profile contacts and listing title in the recipient profile language. A read of the exact private queue job and its exchange determines whether the recipient is the author or requester; lookup failure uses accurate neutral wording without losing the queued notification. No historical jobs are resent.

Messages contain plain text and HTML alternatives. Names and titles are escaped, messenger buttons accept only recognized Telegram, WhatsApp and Viber destinations, and the displayed contact plus the application link remain available if an email client cannot open a messenger deep link. The message explains that the outcome question becomes available after 24 hours, that answering later is fine, and that only the author completes the listing. This is not a reservation deadline.

To switch to a dedicated Gmail account, create and secure that account, enable Google 2-Step Verification, and generate an app password for VratiMe. Back up the private configuration, then change `smtp_user`, `smtp_password`, `from_email` and the sender display name together. Authenticate using `--check` before activating the replacement. Keep the existing sender until the new credentials pass. Separately update Supabase Auth SMTP sender settings if its login/security messages should use the same new address; this does not change the Supabase owner account, database, or users. Never copy the Supabase Management API's masked/HMAC `smtp_pass` value as a usable password. Transfer the original app password through the approved protected input mechanism, never chat, source code or logs.

SMTP acknowledgement is evidence of server acceptance, not inbox delivery or reading. `sent` requires successful `send_message` and a persisted lease-token-matched receipt. Explicit SMTP rejection retries after ten minutes, maximum three attempts. Timeout/disconnect, expired lease, or inability to save an accepted receipt is held (`ambiguous` / `receipt_pending`), never automatically resent; operator reconciliation is required. Message IDs are stable per job, but are not a substitute for SMTP acknowledgement. Logs contain only counts and error classes, no recipient addresses or exception text.

Tests: `python scripts/server/test_vratime_contact_mailer.py`; isolated database fixture: `node scripts/contact-outcome-sql-probe.mjs` (never run generated bootstrap SQL on production). The separate cron migration schedules in-app outcome prompts once a minute; email sending does not depend on browser tabs.
