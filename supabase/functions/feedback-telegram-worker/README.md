# Feedback Telegram background retry worker

Prepared locally for approved reliability item 46. No live Telegram call, live database change, deployment, secret configuration or scheduler installation was performed by this task.

`POST /functions/v1/feedback-telegram-worker` accepts only an empty JSON object `{}` (at most 256 bytes, two-second read limit). It requires exact `X-Feedback-Worker-Secret` authorization against `FEEDBACK_WORKER_SECRET`, 32–256 characters. A user JWT, service API key or a string containing the secret is not sufficient. No user ID, feedback ID, recipient, URL or batch size is accepted from the request.

The release owner configures `verify_jwt=false` for this scheduler endpoint and installs the intended five-minute schedule with its separate secret header. This task leaves `supabase/config.toml` and scheduling unchanged. Required server environment is `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `FEEDBACK_WORKER_SECRET`; optional `FEEDBACK_WORKER_MAX_BATCH` defaults to five and is capped at five. The new entrypoint prefers `VRATIME_TELEGRAM_BOT_TOKEN` / `VRATIME_TELEGRAM_CHAT_ID`, falling back to generic bot variables exactly as the existing user entrypoint does. The original user `feedback-telegram/index.ts` is unchanged.

The CLI-created migration adds service-only `pending_feedback_telegram(maximum default 5)`. It derives each feedback ID and owner ID from queued server rows and returns at most five due `queued`, `failed` or `unconfigured` rows with fewer than five attempts. Future retries, delivered rows, active sending leases, exhausted rows and ambiguous rows are excluded. Expired/invalid sending leases become `ambiguous`; they are never silently returned to the retry queue.

The worker reuses `createFeedbackTelegramDelivery` extracted from the existing user handler. The existing user route still validates Auth, request shape and ownership before calling that factory. The worker supplies only server-derived candidate IDs. Both routes use the same `claim_feedback_telegram`, owner-checked private attachment signing (five-minute URL), Telegram plain-text formatting, existing per-user rate limit, idempotency and `finish_feedback_telegram` receipt logic. Concurrent worker/user calls cannot claim the same active lease twice.

Confirmed Telegram rejection is retained as `failed` and retried only after `next_attempt_at`, with at most five total attempts. Network failures, malformed/unknown acknowledgements and receipt-write failures remain held. The worker never immediately resends a message whose acknowledgement is uncertain. A missing bot configuration retains `unconfigured` without consuming a send attempt; configuration restoration allows a later worker run to proceed. The original stored feedback remains intact throughout.

At most five items are attempted per request. A 100-second request budget, eight-second individual network limits and a conservative remaining-time check can stop earlier, leaving untouched candidates for the next scheduled run. The result includes `processed`, `limit`, `continuationNeeded` and per-feedback receipt states. Continuation is conservatively indicated when the candidate limit is reached, since more due rows may exist beyond the bounded selection. A provider/database failure never exposes bot tokens or raw fetch exceptions, and a delivery is never reported confirmed if its receipt could not be saved.

Verification: `node scripts/feedback-telegram-worker-check.mjs` executes the exact original queue migration plus the new worker migration in PGlite, then drives the real shared delivery and worker handlers through offline HTTP boundaries. Cases cover server-only permissions, candidate bounds/ownership, due/exhausted/held states, strict secret/body authorization, batches, private signing, receipt deduplication, failed retry backoff and unknown receipt holds. The unchanged user-endpoint checks are `node scripts/feedback-telegram-check.mjs`; run their optional actual SQL cases with `--pg-tools=<absolute staging path>`. No actual Telegram calls occur in these checks. Actual deployment/cron setup and the requested real VratiMe feedback smoke test remain with the parent release task.
