# Managed user media

Prepared locally for approved media items 32–36. No live migration, function deployment, signing, upload or deletion was performed during implementation.

## Contract

The browser imports `uploadUserMedia({kind,file,operationId?,expectedUserId?,signal?})` from `src/lib/mediaUploads.js`. `kind` is `avatar`, `listing` or `feedback`; `file` is a JPEG/PNG/WebP Blob. The helper checks the expected session owner, binds that exact bearer token to the request and passes the AbortSignal. It refuses mismatched/cancelled requests with `media_auth_changed`. Keep the same UUID operation ID and identical bytes when retrying. A completed operation returns the same `{url,path,assetId}` without decoding or uploading again. A different file/kind for an existing operation ID is rejected.

An active in-flight lease returns `media_upload_in_progress`. Failed or expired leases can reclaim the **same** asset/path with a fresh claim token. Each claim is counted against the hourly attempt limit; stale tokens cannot prepare/complete a reclaimed operation. Before a Storage write the server persists the encoded SHA-256 and byte count. If the object exists after an uncertain upload, a bounded authenticated download must match this identity before completion; it is never overwritten. A lost database-commit response is resolved by the next idempotent reservation. Different stored bytes require operator reconciliation. Do not mint new operation IDs merely to bypass an uncertain old request.

The request is a raw Blob, not multipart or base64, with `X-Media-Kind` and `X-Operation-Id`. Auth is validated against `/auth/v1/user`; anonymous sessions are refused. The endpoint never accepts a caller-supplied user ID or arbitrary remote URL.

Avatar/listing `url` values are immutable public JPEG Storage URLs. A feedback `url` is **`media:<asset UUID>`**, an opaque private attachment reference that can be passed unchanged to `create_feedback`. `getPrivateMediaUrl(assetId)` accepts either that reference or the UUID, authenticates the caller and returns a 300-second signed URL. Display the URL in a modal/image after the user requests it; do not save signed URLs in feedback records.

Server-side Telegram attachment access uses the service-only RPC `media_private_asset(expected_user_id uuid,target_asset_id uuid)` returning `{path,bucket}` or null, then `POST /storage/v1/object/sign/FEEDBACK-ATTACHMENTS/<path>` with `{expiresIn:300}`. Only the owner or a profile with `app_role` moderator/admin is authorized. Normalize Storage's `/object/sign/...` response by prefixing `<SUPABASE_URL>/storage/v1`; verify the resulting origin and private-bucket path. Keep existing legacy public feedback links readable in the delivery worker; only new feedback attachments use the private bucket.

## Limits and storage policy

- Input: at most 5 MiB, 12 million pixels, width/height at most 6000. Static JPEG/PNG/WebP only; video, SVG, GIF, APNG and animated WebP are refused.
- Output: JPEG re-encode strips profiles/EXIF/text after correcting orientation. Avatar center crop is exactly 512×512 and at most 512 KiB. Other images retain aspect ratio, longest side at most 1600 px and at most 2 MiB. Three bounded JPEG quality attempts (82, 70, 58) are allowed; failure refuses the upload.
- The ImageMagick policy permits only JPEG/PNG/WebP coders, no delegates/filters, no disk cache, one thread. Decoder memory and allocation limits are 96 MiB; maximum four temporary image caches, two-second ImageMagick time limit and 1.5-second transform deadline. One in-flight upload is held per isolate; request reading is limited to ten seconds and each network call to eight seconds. Hosted Edge CPU/memory enforcement still needs deployment validation.
- Per user: 100 MiB across all three buckets, including old files and active reservations, and 30 processing/upload claims per hour, including retries and failed decodes. PostgreSQL serializes reservations per user with a transaction advisory lock. A reservation holds the maximum possible output size for two minutes; reclaim holds it once. Reconciliation of an already stored object does not reserve duplicate capacity. Real Storage sizes are reconciled on every reservation; missing legacy size metadata fails closed. Existing objects are never deleted or rewritten by changing bucket limits.
- Database triggers enforce a maximum of five listing photos (including a distinct cover URL), completed owner assets for new listing/avatar references, and completed private feedback assets. Unchanged legacy references survive updates. New arbitrary URLs or another user's assets cannot be introduced through RPC/direct listing insertion.
- Restrictive INSERT/UPDATE/DELETE policies deny normal JWT writes to AVATARS, LISTING-PHOTOS and FEEDBACK-ATTACHMENTS even if a permissive legacy policy exists. Public listing/avatar downloads and the existing avatar owner metadata SELECT policy remain. Private feedback reads/signing via the ordinary Storage client are denied; only the authorized Edge signing path is supported.

## Publication order and compatibility

Publish the migration, this Edge function and updated browser together after the approved complete release. The prior cached PWA can still display existing public URLs, but its direct Storage uploads will fail once restrictive policies are active. The updated UI must explain that an app update is needed; **do not add a fallback to direct upload**. Database triggers also reject old clients submitting new arbitrary image URLs. No client-side secret/service key is added; the service key is read only from the Edge environment.

The official [Supabase image example](https://supabase.com/docs/guides/functions/examples/image-manipulation) recommends ImageMagick WASM and states that native Sharp is unsupported. Version **0.0.45** is pinned and vendored: the matching self-contained ESM wrapper is `vendor/magick.mjs`; the package's x86 binary is `magick.wasm`; original LICENSE/NOTICE are retained. `vendor/provenance.json` records upstream paths, exact sizes and SHA-256 checksums. Tests load these exact vendored files, not an externally installed substitute. The package's 0.0.45 export points to `dist/x86/magick.wasm`; the earlier `dist/magick.wasm` lookup is not used.

`index.ts` reads `new URL('./magick.wasm', import.meta.url)`. `supabase/config.toml` explicitly includes that binary and license notices as `static_files`, following [Supabase WASM bundling guidance](https://supabase.com/docs/guides/functions/wasm). There is no npm dependency in the function bundle, so a second 15 MB x64 binary cannot be pulled in accidentally. All function-directory files are checked below 20,000,000 bytes (about 16.1 MB currently). Supabase permits [20 MB with local CLI bundling versus 5 MB server-side bundling](https://supabase.com/docs/guides/troubleshooting/edge-function-bundle-size-issues); this function requires local Docker bundling (the default in Supabase CLI2.121.0; do not use `--use-api`) and cannot use the API/static-file deployment path. No deployment command was run. Check the actual bundle before release.

## Verification and cleanup

`node scripts/media-security-check.mjs` executes the actual vendored WASM decoder and exact migration against focused PGlite Auth/Storage fixtures. It imports the real `index.ts` with Node shims only for Deno file/env/serve boundaries, so the entrypoint itself reads and initializes its actual vendored WASM. PGlite lives outside the repository at `../vratime-staged-20261019/.private-pg-tools` (`@electric-sql/pglite@0.5.10`); application dependencies are unchanged. Startup checks verify vendored hashes, static asset paths and the conservative function-directory size budget. SQL/handler tests cover expired/failed claims, stale tokens, ambiguous Storage writes, lost commits, changed stored bytes, retry quotas and exact-bearer cancellation. RED failures were observed before the fixes and saved in the staging review evidence. This is an offline model, not a hosted Supabase runtime.

`media_cleanup_candidates(minimum_age_days default 7)` is service-only and read-only. It reports at most 500 unreferenced Storage objects older than at least seven days and checks profiles/listing covers/listing arrays/feedback references, including legacy URL query strings/fragments. Active reservations/cleanup claims are excluded. `node supabase/functions/media-upload/cleanup-dry-run.mjs --dry-run` (also the default mode) only reports; no .env is loaded and nothing is scheduled.

The prepared operator maintenance command requires both `--execute --confirm-unreferenced-media-deletion`. It handles **managed ledger assets only**: `media_claim_cleanup` rechecks age and references while locking the asset row, then marks it `deleting`. Reference triggers acquire shared row locks and require `complete`, so new references cannot attach during deletion. The command deletes the newly claimed path with the Storage API, then `media_finish_cleanup` verifies Storage metadata absence before recording a `deleted` tombstone. It never deletes Storage metadata directly. Claim tokens protect stale maintenance workers; expired missing-object claims can resume after an uncertain response. Retries cannot resurrect deleted operation IDs. Legacy objects remain report-only because they lack the managed immutable ledger; old publicly stored feedback privacy remains a separate migration decision. **No real deletion or execution-mode maintenance was run.** Tests exercise only injected HTTP and offline fixture metadata.

Publication gates: build the Docker bundle and run the actual Supabase Edge runtime with its [256 MB memory and 2-second CPU limit](https://supabase.com/docs/guides/functions/limits); check cold start, large valid files, signed-link expiry, real Auth/Storage policy denial, network ambiguity and genuinely parallel PostgreSQL sessions near quota. Node/PGlite checks do not prove these hosted limits or live transactions. No live verification result is claimed here.
